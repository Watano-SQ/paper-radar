# V0.7 Scoring, Balance, and Rejects Spec

## Status

Active design note for V0.7.

## Intent

Add transparent rule-based candidate scoring to the weekly candidate report so the report is more useful for later human or LLM screening.

V0.7 does not create a machine-learning recommender and does not produce final reading grades. Candidate levels such as `S_candidate` and `A_candidate` only describe report-stage candidate strength.

## Scope

In scope:

- Load `config/scoring.yaml` through `RuntimeConfig`.
- Score weekly JSONL candidate rows during report generation.
- Keep scoring independent from source clients and SQLite.
- Apply configurable lane balance so one lane cannot dominate the report.
- Generate an optional reject/downrank log for debugging filtering decisions.
- Preserve `--config-dir` and default local CLI behavior.
- Provide `--no-scoring` compatibility behavior for the weekly report.

Out of scope:

- LLM summarization or ranking.
- PDF downloading.
- Zotero, Obsidian plugin, Anki, Telegram, or email integration.
- Vector databases.
- OpenReview, CORE, or IEEE clients.
- Google Scholar or publisher HTML scraping.
- SQLite schema changes or JSONL export format changes.

## Candidate Scoring

Scoring uses only fields already present in exported JSONL candidates:

- title
- abstract
- source
- source_query
- fields
- keywords
- published_date
- year
- DOI / arXiv ID / PMID
- URL / OA URL
- canonical_id
- venue
- work_type

Scoring considers metadata completeness, freshness, source quality, lane keyword matches, cross-domain keyword overlap, review/survey signals, and simple noise penalties.

## Report Behavior

The weekly candidate report remains a candidate pool, not a final reading list.

When scoring is enabled, each selected candidate includes:

- candidate level
- radar score
- score reasons
- penalties

Reject logs are optional and written under the runtime-configured reports directory when requested.
